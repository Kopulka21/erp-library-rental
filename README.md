## Структура зв’язків

- Book (name, author, isbn, publish_year). Одна книга може мати багато примірників: copy_ids (One2many до Copy).
- Copy (book_id, inventory_number, condition). Кожен примірник належить одній книзі: book_id (Many2one до Book, required, `ondelete=‚restrict‘`).
- Member (membership_number, унікальний). Один читач може мати багато видач.
- Loan (copy_id, member_id, loan_date, due_date, return_date, state). copy_id (Many2one до Copy, required), member_id (Many2one до Member, required).

Книга і примірник винесені в окремі моделі, бо одна книга (назва, автор, ISBN) може існувати у кількох фізичних екземплярах з різним станом і інвентарним номером. Видача прив’язана до примірника, а не до книги, бо видається конкретний фізичний екземпляр. Один примірник не може бути в двох активних видачах одночасно.

Member реалізований як окрема модель library.member зі своїми полями, без _inherits від res.partner. Так простіше, бо для бібліотеки потрібні лише ім’я, контакти і номер читацького. Мінус: дані читача не пов’язані зі стандартними контактами.

Відхилень від рекомендованої структури немає.

# library_rental: бізнес-логіка (Практичне заняття 3)

## Обчислювані поля
- `due_date` («Повернути до»): `compute`, `store=True`, `@api.depends('loan_date')`. Дата видачі + 14 днів (константа `LOAN_PERIOD_DAYS = 14`).
- `fine_amount` («Штраф, грн»): `store=True`, `@api.depends('return_date', 'due_date')`. Рахується лише коли `return_date` заповнена і пізніша за `due_date`: дні прострочення × `FINE_PER_DAY` (5 грн/день), в інших випадках 0.
- `is_overdue`: нестор-поле (без `store`), `@api.depends('state', 'due_date')`. Істина, якщо видача активна і `due_date` менша за сьогодні.

## onchange
- `@api.onchange('copy_id')` лише попереджає («Цей примірник уже має активну видачу»), збереження не блокує. У пошуку виключається поточний запис (`_origin.id`).

## Обмеження цілісності (@api.constrains)
1. `copy_id`, `state`: один примірник не може мати двох активних видач. Пошук інших видач виключає `rec.id`. Помилка: «Цей примірник уже виданий: у нього є інша активна видача.»
2. `loan_date`, `due_date`: `due_date` має бути пізніше за `loan_date`. Помилка: «Дата повернення має бути пізніше дати видачі.»
3. `loan_date`, `return_date`: фактична дата повернення не раніше дати видачі. Помилка: «Фактична дата повернення не може бути раніше дати видачі.»

## Ставка штрафу і термін видачі
- Термін видачі: 14 днів (`LOAN_PERIOD_DAYS`). Штраф: 5 грн за кожен день прострочення (`FINE_PER_DAY`). Обидва значення задані константами на початку `models/loan.py`.

## Безпека (Практичне заняття 4)

### Групи доступу
- Категорія «Бібліотека» (у Odoo 19 через `res.groups.privilege`), в ній дві незалежні групи: `group_library_librarian` («Бібліотекар») і `group_library_reader` («Читач»).
- Групи не успадковують одна одну, щоб record rule для Читача не діяв на Бібліотекаря.

### Поле user_id
- `library.member.user_id`: Many2one до `res.users`, не required, з `UNIQUE(user_id)`, щоб один користувач не був привʼязаний до кількох читачів.

### Права доступу (ir.model.access.csv)
- Бібліотекар: read/write/create/unlink = 1 на book, copy, member, loan.
- Читач: лише read на book, copy і loan; на member усі права 0.

### Record rule
- `rule_library_loan_reader` на `library.loan`: домен `[(member_id.user_id, =, user.id)]`, поле `groups` заповнене групою `group_library_reader`. Без `groups` правило стало б глобальним і приховало б видачі навіть від Бібліотекаря та адміністратора.

### Меню
- Корінь «Бібліотека» бачать обидві групи; Книги, Примірники, Читачі, Видачі лише Бібліотекар; «Мої видачі» лише Читач.

### Що довелося виправити після AI-генерації
- У Odoo 19 у `res.groups` немає поля `category_id`: додала запис `res.groups.privilege` і привʼязала групи через `privilege_id`.
- Файл `library_security.xml` підключений у `__manifest__.py` раніше за `ir.model.access.csv`.
- Рядки CSV для Читача не скопійовані з Бібліотекаря (`1,0,0,0` і `0,0,0,0`).

### Перевірка під Читачем

### Заплановане завдання (ir.cron)
- У `library.loan` додала метод `_cron_check_overdue_loans()`: шукає видачі з `state = 'active'` і `due_date < сьогодні` через ORM `search()`.
- Обрала варіант з логуванням, а не `message_post`: `library.loan` не успадковує `mail.thread`, модуль залежить лише від `base`. Додавати залежність `mail` лише заради чаттера — зайве навантаження і ризик зламати форми та права з попередніх практичних.
- Cron зареєстрований у `data/ir_cron_data.xml`: модель `library.loan`, інтервал 1 день, код `model._cron_check_overdue_loans()`. Файл підключений у `__manifest__.py` перед демо-даними.

### Обробка помилок у cron
- Кожна видача обробляється в окремому `try/except`: при помилці пишеться `_logger.exception(...)` з id видачі, і цикл переходить до наступної (`continue`).
- Це важливо саме для cron: поруч немає користувача, який побачить traceback. Без `try/except` один «поганий» запис зупинив би обробку решти, і наступного разу cron знову падав би на тому самому записі.

### Демо-дані
- 7 книг різних авторів; «Основи Odoo» має 3 примірники, щоб показати часткову видачу назви.
- 4 читачі; у Марії Коваль 3 видачі (для звіту з практичного 5).
- Мікс видач: активні, прострочені й повернені. Дати нових видач рахуються відносно поточної дати (`DateTime.today() - relativedelta(days=N)`), тому прострочені видачі для cron є завжди, незалежно від дня демонстрації.

- **Cron:** ручний запуск (Settings → Technical → Scheduled Actions → Run Manually) — у лозі `Cron: знайдено 3 прострочених видач`, три `WARNING` з примірником, читачем і терміном, `fully done`, без `ERROR`.

### AI-рев'ю: cron і сирий SQL
- Cron використовує лише ORM (`self.search()`), без `self.env.cr.execute()`. Сирий SQL обходить кеш ORM, compute-поля і права доступу та record rules з практичного 4; для невеликої бібліотеки потреби в ньому немає.
